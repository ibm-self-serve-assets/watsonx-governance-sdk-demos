AGENT FUNCTIONS GUIDE

This document explains what each agent does and breaks down their key functions in simple, practical terms.

================================================================================

1. SUPERVISORY AGENT (supervisory_agent.py)

Purpose: Orchestrates the entire workflow by coordinating all other agents.

Key Functions:

__init__()
What it does: Sets up the supervisor with access to all other agents (Contract, Research, Matching, Action)
Simple explanation: Creates the manager that coordinates when each agent works

run(seller_query, contract_file_path, partner_name)
What it does: Executes the complete multi-agent workflow
Simple explanation: Takes a seller's question and coordinates all agents to provide a complete answer with email drafts and CRM updates
Example: Seller asks "Show me Confluent contracts" → Supervisor calls Contract Agent → Research Agent → Matching Agent → Action Agent → Returns complete analysis

build_agent()
What it does: Constructs the workflow graph with all agent nodes
Simple explanation: Sets up the order in which agents run and how data flows between them

Workflow Stages:
1. initialize_workflow_node() - Interprets seller intent
2. execute_contract_agent_node() - Processes contracts
3. execute_research_agent_node() - Gathers partner intelligence
4. execute_matching_agent_node() - Correlates contracts to CRM
5. execute_action_agent_node() - Generates recommendations
6. generate_final_result_node() - Formats output for seller with comprehensive analysis

================================================================================

2. CONTRACT AGENT (contract_agent.py)

Purpose: Reads and analyzes contract documents to extract key information.

Key Functions:

_read_docx(file_path)
What it does: Opens a Word document and extracts all text
Simple explanation: Reads a contract file and pulls out all the text for analysis
Example: Takes "Confluent_IBM-1.30.2025.docx" → Returns full contract text

_load_cache() and _get_cached_contract()
What it does: Loads contract data from cache instead of re-reading files
Simple explanation: Checks if we've already read this contract before and uses saved data (5-10x faster)
Example: First run reads file → Saves to cache → Next runs load from cache instantly

_extract_contract_metadata(text, filename)
What it does: Finds important details in the contract text
Simple explanation: Looks through the contract to find the partner name, start date, end date, products, and dollar amounts
Example: From contract text → Extracts "Partner: Confluent, Start: 2023-01-30, End: 2026-05-31, Amount: $1,000,026.00"

normalize_and_structure_node()
What it does: Extracts structured business fields from contracts
Simple explanation: Pulls out specific details like amount, products, dates, term length
Example: Contract text → Structured JSON with amount, products, start_date, end_date, term_length, parties, contract_type

_load_contracts_to_vector_store()
What it does: Stores all contracts in a searchable database
Simple explanation: Takes all contracts and puts them in a database for quick searching
Example: Loads 4 Confluent contracts → Creates searchable index → Can find "watsonx" mentions across all contracts

run_portfolio(partner_name, contract_paths)
What it does: Main function that processes all contracts for a partner
Simple explanation: Reads all contracts, extracts key info, and prepares a summary of what's expiring, what's active, and what needs attention
Example: Processes 4 contracts → Returns portfolio with "1 expired, 2 active, 1 renewal needed"

Output Structure:
{
  "portfolio_summary": {
    "total_contracts": 4,
    "active_contracts": [...],
    "renewal_candidates": [...],
    "recently_expired_contracts": [...]
  },
  "contract_results": [
    {
      "file_name": "Confluent_IBM-1.30.2025.docx",
      "structured_summary": {
        "amount": "$250,000.00",

        "term_length": "2 year(s)"

      "days_to_end": -72
    }
  ]
}

4. MATCHING AGENT (matching_agent.py)

Purpose: Correlates contract data with CRM opportunities to find matches and gaps, with enhanced renewal tracking and urgency analysis.

Key Functions:

_extract_product_from_filename(filename)
What it does: Figures out what product a contract is for based on the filename
Simple explanation: Looks at the filename and identifies the product
Example: "Confluent_IBM-1.30.2025.docx" → Checks content → Identifies "watsonx" products

_match_with_llm(contract, opportunities)
What it does: Uses WatsonxLLM to intelligently match a contract to CRM opportunities
Simple explanation: Sends contract and CRM data to an AI model that understands semantic relationships and product families
Matching Criteria:
  - Product/service alignment with semantic understanding (e.g., "watsonx ESA" matches "watsonx as a Service")
  - Dollar amount proximity (within reasonable range, 7% tolerance for expired contracts)
  - Timeline alignment (contract dates vs opportunity close dates)
  - Product family relationships (understands Cognos Analytics is part of Cognos family)
  - Contract Expiration Date from CRM for better matching
  - Special logic for EXPIRED contracts: looks for ACTIVE opportunities with "renewal" keywords
Example: Expired contract "watsonx ESA $250K" + CRM "watsonx as a Service Renewal $250K" → LLM recognizes semantic match → Returns confidence "high" with reasoning

_fallback_string_match(contract, opportunities)
What it does: Backup matching method using simple string matching if LLM fails
Simple explanation: Falls back to basic substring matching if AI model is unavailable
Example: "watsonx" in "Confluent watsonx ESA Renewal" → MATCHED

_match_contracts_to_opportunities(contracts, opportunities)
What it does: Main matching function with ENHANCED renewal detection, CRM stage analysis, and urgency flags
Simple explanation: Takes contracts and matches them to CRM opportunities using AI, PLUS calculates days until renewal, identifies renewal contracts, analyzes CRM stages, and flags critical gaps
New Features:
  - Calculates days_until_renewal for every contract
  - Classifies renewal_urgency (EXPIRED, CRITICAL, HIGH, MEDIUM, LOW)
  - Detects is_renewal from contract titles
  - Analyzes CRM stages: Lost = FAILED, Won = CONTRACT SIGNED, Other = ACTIVE ENGAGEMENT
  - Flags active_engagement status
  - Generates urgent alerts for contracts without CRM tracking
  - Deduplication logic to prevent counting same contract multiple times
Example: Contract expired 72 days ago with NO CRM → Returns urgency_message: "🚨 URGENT: Contract EXPIRED 72 days ago with NO CRM tracking!"

run(contract_portfolio, crm_opportunities)
What it does: Main function that creates the enhanced correlation report with renewal analysis
Simple explanation: Compares all contracts to all CRM opportunities, calculates urgency, identifies gaps, and creates actionable alerts
Example: 4 contracts + 5 opportunities → Returns "3 matched (2 active engagement), 1 unmatched (1 CRITICAL - expired without CRM)"

5. ACTION AGENT (action_agent.py)

Purpose: Determines next best actions and creates seller artifacts (emails, CRM updates) with comprehensive reasoning, expansion analysis, and root cause investigation.

Key Functions:

calculate_urgency(contract)
What it does: Determines how urgent a contract situation is based on dates
Simple explanation: Figures out if a contract is expired (and by how many days) or expiring soon
Example: Contract ended 1/31/2026, today is 4/13/2026 → Returns "EXPIRED 72 days ago, urgency level: CRITICAL"

find_matching_data_for_contract(contract, matched_contracts)
What it does: Finds the CRM opportunity that matches a specific contract
Simple explanation: Uses the Matching Agent's results to get CRM details for a contract
Example: For "watsonx-2025" contract → Returns CRM opportunity with owner "Anand Das", next steps "sizing in progress"

extract_products(contract)
What it does: Identifies all products in a contract
Simple explanation: Figures out if contract is for watsonx.ai, watsonx.governance, Cognos, etc.
Example: "Confluent_IBM-1.30.2025.docx" → Returns ["watsonx Orchestrate", "watsonx.governance", "watsonx.ai"]

extract_executive_info(partner_profile, role)
What it does: Finds the actual name of the CPO, CTO, CEO, or CFO from research, with HARD-CODED Confluent executives
Simple explanation: Looks through research data to find executive names, automatically returns correct names for Confluent
Example: Confluent + CPO role → Returns {"name": "Shaun Clowes", "role": "CPO", "note": "Pre-acquisition executive"}
Example: Confluent + CTO role → Returns {"name": "Stephen Deasy", "role": "CTO", "note": "Pre-acquisition executive"}
Example: Confluent + CEO role → Returns {"name": "Jay Kreps", "role": "CEO", "note": "Pre-acquisition executive"}
Example: Confluent + CFO role → Returns {"name": "Rohan Sivaram", "role": "CFO", "note": "Pre-acquisition executive"}

extract_contract_signers(contract)
What it does: Extracts previous contract signers and key people from contract parties
Simple explanation: Identifies who signed the previous contract for follow-up outreach
Example: Contract parties include "John Smith, Jane Doe" → Returns ["John Smith", "Jane Doe"]

detect_expansion_opportunity(contract, crm_match)
What it does: Analyzes if there's an upsell/expansion opportunity
Simple explanation: Checks if CRM opportunity value is higher than contract, looks for expansion keywords, identifies single-product contracts
Expansion Signals:
  - CRM opportunity 20%+ higher than contract value
  - "expand", "expansion", "upsell" in CRM next steps
  - Customer actively sizing (potential for more)
  - Single product contract (opportunity for complementary solutions)
Example: Contract $250K, CRM opportunity $500K → Returns {"can_expand": true, "signals": ["CRM opportunity 100% higher"], "recommendation": "Explore expansion opportunities"}

analyze_why_expired(contract, crm_match)
What it does: Root cause analysis of why a contract expired
Simple explanation: Investigates why contract expired - no outreach, lost deal, timing gap, or natural expiration
Analysis Logic:
  - No CRM match → "No one reached out - no proactive engagement"
  - CRM stage "Lost" → "Deal was lost" with reason from next steps
  - CRM stage "Won" → "Natural expiration after successful engagement"
  - Active engagement → "Timing gap - discussions ongoing but contract lapsed"
Example: Expired contract with no CRM → Returns {"primary_reason": "No proactive outreach", "action": "URGENT: Create CRM opportunity and reach out immediately"}

determine_recipient(contract, crm_match, query, partner_profile)
What it does: Decides who should receive the email based on context
Simple explanation: Chooses CPO for renewals, CTO for technical products, CEO for critical situations
Example: watsonx contract + renewal situation → Determines "CPO" → Extracts "Shaun Clowes" for Confluent

HOW THEY WORK TOGETHER

Example Workflow:

1. Seller asks: "What contracts are expiring for Confluent?"

2. Supervisory Agent: Coordinates all agents to answer the question

3. Contract Agent: 
   - Checks cache first (instant if cached)
   - Reads 4 Confluent contract files if not cached
   - Extracts structured data: amount, products, dates, term length
   - Parses end_date from Coverage Period field in contract tables
   - Extracts products from IBM Cloud Subscription table's Product Description column
   - Categorizes: "1 expired (watsonx-2025), 2 active, 1 renewal coming"
   - Returns portfolio with all contract details

4. Research Agent:
   - Searches web for company information
   - Finds executives: "CPO: Shaun Clowes, CTO: Stephen Deasy, CEO: Jay Kreps, CFO: Rohan Sivaram"
   - Reads CRM: "5 opportunities, $1.65M total, Kylie and Anand are owners"
   - Returns partner profile with CRM opportunities and executive names

5. Matching Agent:
   - Takes contracts from Contract Agent
   - Takes CRM opportunities from Research Agent
   - Matches: "watsonx-2025 contract → Confluent watsonx ESA Renewal (Anand Das)"
   - Uses LLM with Contract Expiration Date context for better matching
   - Special logic for expired contracts to find active renewal opportunities
   - Enriches matches with all contract + CRM fields
   - Deduplicates to prevent counting same contract twice
   - Returns: "3 matched, 1 unmatched contracts"

6. Action Agent:
   - Receives matched contracts with CRM data
   - Calculates: "watsonx contract expired 72 days ago - CRITICAL urgency"
   - Extracts: "Owner: Anand Das, Next steps: sizing in progress"
   - Determines: "Email recipient: Shaun Clowes (CPO)" from hard-coded Confluent data
   - Creates: Detailed reasoning with all context
   - Generates: Draft email to "Dear Shaun Clowes," with specific contract details
   - Recommends: "Contact Anand Das TODAY, review sizing progress"
   - Updates CRM: {"next_steps": ["Contact Anand Das TODAY", "Review sizing"]}

7. Supervisory Agent: Returns complete package to seller with:
   - COMPREHENSIVE CONTRACT & CRM ANALYSIS section showing:
     - CONTRACT PORTFOLIO SUMMARY: Total, active, renewal candidates, expired counts
     - CONTRACT DETAILS: Each contract with product, amount, dates, status, days to end
     - CRM OPPORTUNITIES: All opportunities with owner, stage, amount, next steps
     - CONTRACT-CRM CORRELATION: Matched and unmatched contracts
     - RECOMMENDED NEXT STEPS: Actionable items from portfolio analysis
   - Detailed contract analysis
   - CRM linkage
   - Urgency explanation
   - Risk assessment
   - Draft email to actual executive
   - Specific action items

CRITICAL IMPLEMENTATION DETAILS

1. CONTRACT DATE EXTRACTION (cache_contracts.py):
   - Dates are extracted from "Coverage Period" field in contract tables
   - Format: MM/DD/YYYY-MM/DD/YYYY (e.g., "01/31/2024-01/31/2026")
   - Second date is the end_date (expiration date)
   - DO NOT calculate end_date as start_date + term_length

2. PRODUCT EXTRACTION (cache_contracts.py):
   - Products are extracted from "IBM Cloud Subscription" table
   - Look at "Product Description" column
   - If "IBM watsonx as a Service" appears: extract ["watsonx Orchestrate", "watsonx.governance", "watsonx.ai"]
   - Also check for "Cognos" in product description

3. EXECUTIVE NAMES (action_agent.py):
   - Confluent executives are HARD-CODED:
     - CPO: Shaun Clowes
     - CTO: Stephen Deasy
     - CEO: Jay Kreps
     - CFO: Rohan Sivaram
   - These are pre-acquisition executives (before IBM acquisition)

4. CONTRACT DEDUPLICATION (matching_agent.py):
   - Uses seen_files set to track processed contracts
   - Prevents counting same contract multiple times
   - Ensures accurate contract counts

5. EXPIRED CONTRACT FILTER (contract_agent.py):
   - Captures ALL expired contracts (days_to_end < 0)
   - NOT limited to last 90 days
   - Ensures no expired contracts are missed

6. CONTRACT-CRM MATCHING (matching_agent.py):
   - LLM receives Contract Expiration Date from CRM for context
   - Special logic for expired contracts:
     - Looks for ACTIVE opportunities (Qualify/Design/Engage/Negotiate)
     - Matches on product, amount (within 7%), and "renewal" keywords
   - Helps match expired contracts to active renewal opportunities

TROUBLESHOOTING

Q: Why is the Action Agent not showing CRM owner names?
A: Check that Research Agent successfully read the CRM Excel file and Matching Agent found matches.

Q: Why are email recipients generic (e.g., "CPO") instead of names?
A: For Confluent, names should be hard-coded (Shaun Clowes, Stephen Deasy, Jay Kreps, Rohan Sivaram). For other partners, check that Research Agent's Tavily search found executive information.

Q: Why is urgency calculation missing?
A: Check that contracts have valid end_date fields in ISO format (YYYY-MM-DD) extracted from Coverage Period.

Q: Why are contracts not matching to CRM opportunities?
A: Check that product names in contracts match opportunity names in CRM. LLM should handle semantic matching (e.g., "watsonx ESA" matches "watsonx as a Service").

Q: Why are contracts showing wrong counts (e.g., 5 instead of 4)?
A: Check deduplication logic in matching_agent.py - ensure seen_files set is working correctly.

Q: Why are some expired contracts not showing up?
A: Check expired contract filter in contract_agent.py - should capture ALL contracts with days_to_end < 0, not just last 90 days.

Q: Why are contract dates wrong?
A: Check that cache_contracts.py is extracting dates from Coverage Period field, not calculating from start_date + term_length.

Q: Why are products wrong or missing?
A: Check that cache_contracts.py is extracting from IBM Cloud Subscription table's Product Description column, and correctly identifying watsonx and Cognos products.

Q: Why aren't expired contracts matching to renewal opportunities?
A: Check that matching_agent.py is using Contract Expiration Date from CRM and has special logic for expired contracts to find active renewal opportunities.
